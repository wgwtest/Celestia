## 1. 本步骤定位

Step24 对应《02-15-Celestia-MVC总体决策与路线图》的阶段 A：原业务链与责任归属基线。

它解决的不是“下一批代码放到哪个目录”，而是先回答以下基础问题：

1. 原 Celestia 每类核心业务能力从哪里进入，真实修改什么状态。
2. `Simulation`、`Observer`、`Selection`、`Universe`、Catalog、Body、Timeline、ReferenceFrame 等对象由谁创建、持有、写入、读取和销毁。
3. 原 View3D 在生成场景列表、做可见性判断和实际绘制时读取了哪些 Model、会话、资源和表现状态。
4. 哪些能力属于 Model 事实或计算，哪些属于 Controller 命令与策略，哪些属于 View 中立投影，哪些是 View3D 私有能力。
5. 哪些现有类型是混合对象，必须字段级拆分，不能整类迁移。
6. 后续状态闭环、资源治理、输出分层和模板 View 迁移应按哪些真实依赖切片。
7. 每个迁移切片以后如何通过统一 exe 和跨进程模板 View 两条路径验证。

Step24 完成后，只允许得出“后续实施计划具备事实输入”，不能得出“Model 已解耦”或“可以直接迁移 View3D”。

## 4. 分析单位与分类规则

### 4.1 业务能力族

Step24 至少覆盖以下能力族；执行时可以拆分子项，但不能遗漏整个能力族：

| ID | 能力族 | 主要问题 |
|---|---|---|
| `CAP-BOOT` | 配置、Catalog 加载和运行对象创建 | 谁创建 Universe、Catalog、资源路径、Simulation、Renderer |
| `CAP-TIME` | 时间推进、暂停、倍速和时间设置 | 权威时间在哪里，谁写入，谁读取 |
| `CAP-OBS` | Observer、参考系、位置、方向、FOV | 会话状态、Model 计算和 View 投影如何交织 |
| `CAP-SEL` | Selection、Picking、标记和对象引用 | 句柄、权威选择状态和 View 命中计算如何区分 |
| `CAP-NAV` | Center、Goto、Follow、Chase、Orbit、旋转 | 命令、状态修改、轨迹计算和反馈链 |
| `CAP-CATALOG` | Star、DSO、SolarSystem 三类 Catalog | 数据构建、索引、资源绑定和生命周期 |
| `CAP-VIS` | 可见性、裁剪、星等、LOD 和场景列表 | 哪些是通用场景计算，哪些是 View3D 策略 |
| `CAP-STAR` | 恒星、星场、光晕和恒星标签 | Model 数据、投影数据和 View3D 绘制输入 |
| `CAP-DSO` | Galaxy、Nebula、Cluster 等 DSO | Catalog、RenderPolicy、资源和具体绘制 |
| `CAP-BODY` | 行星、卫星、小天体、航天器 | Body、Timeline、Frame、位置姿态和分类 |
| `CAP-SURFACE` | Surface、纹理、网格、材质和替代表面 | Model/场景外观/资源引用/GPU 缓存分界 |
| `CAP-ATM` | Atmosphere、Cloud、Shadow、Ring、Comet Tail | 计算事实、光学参数、资源和 View3D 实现分界 |
| `CAP-ORBIT` | Orbit、Trajectory、OrbitSampler 和轨道绘制 | 轨道事实、采样、列表和曲线绘制分界 |
| `CAP-ANNOT` | Label、Marker、ReferenceMark、Grid、Boundary | 语义、投影、布局和绘制分界 |
| `CAP-POLICY` | RenderFlags、LabelMode、StarStyle、Ambient、TextureResolution | Controller 命令、View 状态和持久化边界 |
| `CAP-RESOURCE` | TexturePaths、GeometryPaths、RenderAssets、Manager、Shader、Framebuffer | 公共描述、定位、传输、CPU/GPU 缓存分界 |
| `CAP-SCRIPT` | Legacy Script、Lua/CELX 对业务和渲染状态的访问 | 非桌面输入消费者是否改变归属结论 |
| `CAP-FEEDBACK` | HUD、Overlay、状态提示和脚本/UI 反馈 | Controller 结果、View 私有反馈和平台 UI 分界 |

按钮、菜单和脚本命令只能挂在上述能力族下作为触发入口，不能独立成为架构切片。

### 4.2 目标责任类别

每个对象、状态、函数或字段只能采用以下目标类别之一，或明确标记为待拆分：

| 类别 | 判定含义 |
|---|---|
| `M-Core` | 天体对象、客观状态、领域计算或与具体 View 无关的索引 |
| `M-Session` | Model Host 中唯一权威的运行会话状态；是否最终保留独立子层由证据决定 |
| `C-Command` | 输入解释、命令生成、控制策略和操作编排，不保存第二份业务事实 |
| `Projection` | 从权威事实派生、可供多个 View 使用的中立场景数据 |
| `Resource-Common` | 稳定资源描述、路径定位、内容标识和数据传输，不持有具体 GPU 对象 |
| `View3D-Private` | 只有 View3D 需要的可见性策略、布局、着色、GPU 缓存或绘制实现 |
| `View-Common` | 至少两个真实 View 具有相同语义和生命周期的公共 View 能力 |
| `App-Assembly` | 启动、配置、进程组装和平台无关的应用编排 |
| `Platform-UI` | Qt、Win32、SDL 的窗口、菜单、对话框和平台事件适配 |
| `Split-Required` | 当前类型或函数同时包含多个责任，必须字段级或函数级拆分 |
| `UNRESOLVED` | 证据不足，必须记录缺口和决策前提，禁止猜测 |

`View-Common` 不能仅凭“未来可能复用”判定，必须指出第二个真实消费者或明确的同语义接口。

### 4.3 证据等级

| 等级 | 含义 | 使用限制 |
|---|---|---|
| `F0` | 源码直接事实：成员、调用、读写、构造、销毁、include 或 CMake 关系 | 可直接支撑当前事实 |
| `F1` | 多个 F0 事实组合出的跨文件结论 | 必须列出组成证据 |
| `D0` | 基于事实的目标设计判断 | 必须说明替代方案和选择原因 |
| `U0` | 未决问题 | 必须写出缺少的证据和解决阶段 |

任何目标归属都不能只写“按 MVC 原则应当如此”，至少需要一个 `F0` 或 `F1` 证据。

## 6. 固定表格格式

### 6.1 业务能力矩阵

| 字段 | 必填内容 |
|---|---|
| Capability ID | `CAP-*` 稳定编号和业务名称 |
| Trigger | 键盘、菜单、脚本、初始化或 tick 等入口 |
| Authoritative State/Object | 被真实读取或修改的状态/对象 |
| Writer | 创建者和写入函数 |
| Reader/Consumer | Model 计算、Renderer、Adapter、脚本或平台消费者 |
| Derived Data | 可见列表、投影、采样、资源描述等派生数据 |
| Feedback | HUD、Overlay、状态返回或无反馈 |
| Current Boundary Problem | 当前交织或重复所有权 |
| Target Category | 第 4.2 节类别或 `UNRESOLVED` |
| Migration Slice | 后续最小迁移单元，不写实现细节 |
| Verification | 状态断言、对象断言、截图、人工检查或豁免理由 |
| Evidence | `E-*` 证据编号 |

### 6.2 对象与状态所有权矩阵

| 字段 | 必填内容 |
|---|---|
| Object/State | 类型、成员或状态族 |
| Created By | 构造或加载入口 |
| Owned By | 当前内存所有者和生命周期 |
| Written By | 所有写入者，不能只列主路径 |
| Read By | 主要读取者和脚本/前端交叉消费者 |
| Destroyed By | 销毁、reset 或全局 side table 清理路径 |
| Current Physical Location | 当前目录和构建目标 |
| Target Logical Owner | 目标责任类别 |
| Target Physical Candidate | 候选目录/目标，未决时不得强填 |
| Split Needed | 字段级/函数级/无 |
| Evidence/Reason | 证据与判断理由 |

### 6.3 原 View3D 读集矩阵

| 字段 | 必填内容 |
|---|---|
| Render Phase | 场景收集、排序、裁剪、标注、资源解析、绘制等阶段 |
| Entry Function | `Renderer` 或子 renderer 入口 |
| Inputs Read | 读取的对象、状态、字段和资源 |
| Computation | 该阶段执行的计算 |
| Output/Internal State | 生成的列表、annotation、GPU 数据或画面 |
| Other Consumers | 是否存在非 View3D 消费者 |
| Target Category | `Projection`、`View3D-Private`、`Split-Required` 等 |
| Evidence | 具体源码位置 |

### 6.4 源码证据记录

每条证据采用：

```text
E-<能力族>-<三位序号>
文件：相对路径
符号：类/函数/成员
基线行：执行时记录的行号
动作：CREATE / READ / WRITE / DESTROY / CALL / BUILD
事实：一句可由源码直接验证的描述
等级：F0 / F1 / D0 / U0
支持：对应矩阵行或判断
```

行号只用于基线定位；符号名才是跨提交的稳定锚点。

## 8. Step24 验收标准

Step24 同时满足以下条件才算完成：

1. 第 4.1 节全部能力族均有业务链、证据、目标归属或明确未决项。
2. 创建链、运行链、绘制链三张总图与详细矩阵一致。
3. `Simulation`、`Observer`、`Selection`、Timeline、ReferenceFrame 的权威状态和主要读写者已说明。
4. Star、DSO、SolarSystem 三类 Catalog/Builder 完成横向比较，不把 SolarSystem 再次误判为唯一特殊对象。
5. 原 View3D 的场景收集、可见性、列表、资源、具体绘制和 Annotation 阶段均有读集矩阵。
6. `Surface`、`Atmosphere`、Ring、RenderAssets 至少达到字段级或函数组级判断。
7. Renderer 内部计算没有因文件位置自动判为 View 私有；公共能力也没有因“可能复用”被提前上提。
8. Qt、Win32、SDL 和脚本 API 已用于交叉检查其他写入者/消费者，但没有扩展成平台 UI 分析。
9. 每个目标归属都有 F0/F1 证据，或标为带关闭条件的 `UNRESOLVED`。
10. 每个迁移切片都有前置依赖、真实所有者、目标责任、重复实现处理和双轨验证方法。
11. 每项业务能力都有验证方式或明确豁免理由。
12. 工作区没有任何程序文件变更。
13. 用户完成人工评审并确认 Step24 结论。

## 9. 不足以验收 Step24 的条件

以下任一结果都不能单独说明 Step24 完成：

1. 生成了更多类图或目录图。
2. 找到了很多 `Renderer::` 调用。
3. 把所有类型都填写了一个 MVC 标签。
4. 扫描台账数量下降或未变化。
5. 统一 exe 回归仍然通过。
