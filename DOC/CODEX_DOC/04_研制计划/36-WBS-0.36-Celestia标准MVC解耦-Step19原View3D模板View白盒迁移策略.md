# Celestia 标准 MVC 解耦 Step19 原 View3D 模板 View 白盒迁移策略

## 1. 目标

Step19 重新开始 View 层工作。目标不是继续增强一个旁路的新 View3D，也不是按截图效果仿写一个弱实现，而是把现有原 View3D 作为业务真相，逐段白盒迁移并适配为第一个标准模板 View。

完成本阶段后，后续新增的 2D、3D、BS 前端或其他 View，应能参照同一组织方式接入，而不是让原 View3D 继续占据特殊位置。

## 2. 当前边界

当前分支已回退到 Step18 最终提交：

```text
a3a5975 docs: record final Step18 verification
```

Step19-Step86 旧路线不再作为后续依据。尤其是旧 Step19-Step57 中围绕 `src/celruntime/view3d` 扩展弱 View3D 视觉提示、visual plan、probe 的路线，不得继续作为架构方向。

当前可保留的基础包括：

```text

src/celestia/viewproviders/     当前 View 注册连接层

新增 View 可以通过删除一个私有目录完整移除。
```

## 3. 核心工作原则

### 3.1 原源码是业务真相

原 View3D 的真实行为以现有源码为准，主要来源是：

```text
src/celengine/view3d/
src/celrender/view3d/
src/celestia/
```

截图对比只作为验收手段，不作为黑盒仿写依据。

### 3.2 白盒能力迁移，不做机械搬文件或旁路复制

迁移对象不是某个文件本身，而是原源码中一段 View 私有能力的归属、依赖和接入方式。执行时应按源码实际形态选择迁移手段：

```text
职责单一的文件:
  可以整体移动到模板 View 目录，并同步适配 CMake、include、命名空间、生命周期入口和 provider 接入。

职责混杂的文件:
  不得整体搬迁。应抽出属于 View 的类、函数或数据结构，迁移到模板 View；原位置只保留非 View 职责。

依赖不适合直接带入的代码:
  不得为了编译把旧 View 依赖整包拖进模板 View。应判断依赖性质，分别做 View 私有迁移、共享模块抽取、接口化或应用层适配。
```

标准迁移方式是：

```text
识别一段原 View3D 私有能力
-> 判断它是职责单一、职责混杂还是依赖不适合直接带入
-> 选择整体移动、拆分抽取、共享化或适配重建
-> 修正 CMake、include、命名空间、生命周期和接入点
-> 编译和回归验证
-> 确认旧位置不再长期保留同一份 View 私有能力
-> 继续下一段
```

禁止把原实现整包复制到新目录，同时让旧目录继续承担完整运行职责。临时兼容层必须有明确删除条件，不能作为长期兜底。

### 3.3 所有 View 平权

最终组织形态应让原 View3D 与后续新 View 占据同等位置。目标形态可以是：

```text
src/celviews/
  view3d_legacy/
  view2d_debug/
  view3d_mvc/
  bs_frontend/
```

`view3d_legacy` 是第一个模板 View，不是临时实验目录。它承接原 View3D 的组件化结果，并给后续 View 提供组织样式参考。

### 3.4 共性能力必须真实可复用

拆出的代码只能落在三类位置：

```text
View 私有实现:
  放入对应 View 自己的目录，例如 src/celviews/view3d_legacy/

跨 View 共性能力:
  放入清晰的共享模块，例如后续可建立 src/celviewcommon/ 或保留在真正通用的底层模块。

非 View 职责:
  继续留在 Model、Controller、应用层或底层工具模块中。
```

如果某段代码只有原 View3D 自己能用，就不应伪装成共享模块。如果某段能力多个 View 都能用，也不应藏在 `view3d_legacy` 私有目录中。

### 3.5 `celruntime` 不承载具体 View 私有实现

`src/celruntime` 的职责是 runtime、协议、进程、transport、assembly、View 抽象和通用服务。它不应成为某一个具体 View 的主工作区。

如果 `src/celruntime/view3d` 后续仍存在，只能作为过渡对象被审计、迁移或删除，不能继续扩大。

## 4. 目标模板 View 结构

第一轮目标不是一次性搬完整 Renderer，而是先建立模板边界。候选结构如下：

```text
src/celviews/view3d_legacy/
  CMakeLists.txt
  README.md
  provider/
    view3dlegacyprovider.cpp
    view3dlegacyprovider.h
  lifecycle/
    view3dlegacyruntime.cpp
    view3dlegacyruntime.h
  app_glue/
    sdl 或 CelestiaCore 连接适配，只有确实属于 View 接入的代码才能放入
  renderer/
    从原 View3D 白盒迁移并适配后的私有渲染实现
  resources/
    只服务该 View 的资源管理适配
  input/
    只服务该 View 的输入解释适配
  private/
    暂未细分但已确认属于该 View 的私有实现
```

该结构不是最终固定目录名清单。每个子目录必须通过源码审计确认职责后再创建，不能为了形式完整提前填充空目录。

## 5. 迁移对象分类规则

每次迁移前，必须先给候选代码分类：

| 类型 | 判断标准 | 处理方式 |
| --- | --- | --- |
| View3D 私有实现 | 只服务原 View3D 绘制、资源、Overlay、View 状态或 GL 细节 | 迁移并适配到 `src/celviews/view3d_legacy/` |
| 跨 View 共性能力 | 2D、3D、BS 前端或未来 View 都能复用 | 抽到共享模块 |
| Model 业务状态 | Universe、Simulation、Selection、Observer、Catalog 等业务状态 | 保留在 Model/engine 合适位置 |
| Controller 行为 | 输入解释、命令语义、导航意图、脚本命令 | 进入 Controller 或应用输入层，不放 View 私有渲染目录 |
| 应用层连接 | SDL/Qt/Win32 窗口、主循环、菜单、配置和启动 glue | 保留在 `src/celestia/` 或明确适配层 |

分类不清楚的代码不得迁移。先写审计结论，再执行移动。

## 6. 每段白盒迁移的固定流程

每个迁移切片必须独立完成以下步骤：

1. 选定候选能力、候选文件或候选函数组。
2. 记录它当前所在路径、被哪些目标编译、被哪些文件 include。
3. 判断它属于 View 私有、共享能力、非 View 职责中的哪一类。
4. 先补一个边界验证点，证明迁移后仍能被正确编译或调用。
5. 根据分类选择整体移动、拆分抽取、共享化或适配重建。只有职责单一的整文件迁移才允许整体移动并保留历史。
6. 更新 CMake target、include 路径、命名空间、构造方式和生命周期接入。
7. 编译相关 target。
8. 运行最小相关 CTest。
9. 运行 Quick 兼容回归，确认普通单 exe 原能力未退化。
10. 如果影响三进程 runtime，补跑 runtime smoke。
11. 检查旧路径中不再长期保留同一份 View 私有能力；如需短期过渡层，必须写明删除条件。
12. 更新 Step19 迁移记录。

每个切片通过后才能进入下一个切片。

## 9. 明确禁止项

禁止继续执行以下做法：

```text
在 src/celruntime/view3d 继续堆具体 View3D 私有效果。
按截图黑盒仿写原 Celestia 画面。
复制原 View3D 后长期保留两套完整实现。
机械搬迁文件但不处理依赖、命名空间、生命周期和 provider 接入。
把只有 view3d_legacy 自己能用的代码放进共享目录。
把 runtime/provider 基础设施当作某个 View 的私有工作区。
用 telemetry 通过代替用户可见场景验证。
```

## 10. 完成标准

Step19 不以“画面新增效果”为完成标准。Step19 的完成标准是：

```text
1. 原 View3D 源码归属矩阵完成。
2. view3d_legacy 模板 View 的目标组织方式明确。
3. 第一批可迁移、暂缓迁移、禁止迁移对象清单明确。
4. 每段白盒迁移的验证门槛固定。
5. CODEX_START_HERE.md 指向新的 Step19 工作策略。
6. 后续任何 View 工作都不能绕过该策略。
```

只有进入 Step19.3 及以后，才开始实际移动源码。
