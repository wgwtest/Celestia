# Celestia 标准 MVC 解耦 Step19.0 模型控制视图边界复审

## 1. 目标

本审计用于回答一个前置问题：在开始原 View3D 模板 View 迁移前，当前 Model / Controller / View 边界是否足够可靠。

结论先行：

```text
Step18 是可运行的中间态基线，不是 Model 层完全锁死点。
原 Celestia 核心对象仍被保留，核心计算能力没有被重新造假。
但源码依赖、运行时输出和资源加载边界都没有达到标准 MVC 下的干净状态。
```

因此，Step19 不应直接进入 View3D 代码搬迁。必须先把 Model、Controller、View、Adapter、Runtime Projection 的职责重新审计清楚。

## 2. 审计范围

本轮审计覆盖：

```text
src/celengine/model/
src/celengine/controller/
src/celengine/adapter/
src/celruntime/model/
src/celruntime/viewframe.h
src/celruntime/protocol/sceneprotocol.h
src/celengine/CMakeLists.txt
tools/mvc/
```

本轮不做 C++ 程序修改，不移动源码，不调整 CMake target，只记录边界事实和后续治理顺序。

## 3. 分层状态结论

| 层面 | 当前判断 | 说明 |
| --- | --- | --- |
| 原始核心能力 | 基本保留 | `Universe`、`Simulation`、`Body`、`Star`、`Selection`、`Observer` 等仍来自原 Celestia。 |
| CMake 初步拆分 | 部分成立 | 已有 `celestia_model`、`celestia_controller`、`celestia_view_adapter`、`celestia_view3d` 对象库。 |
| Model 源码边界 | 不干净 | `model` 仍直接或间接引用 View3D、Adapter、可视标记和生命周期适配层。 |
| Controller 源码边界 | 不干净 | `Simulation` 暴露 active observer、多视图相关状态，并存在 View3D 头文件引用。 |
| Adapter 职责 | 过宽且混杂 | 同时承载资源加载、渲染资产、拾取、runtime 输出投影等多类职责。 |
| Runtime Model 输出 | 只能算早期投影 | `ViewFrame` / `SceneFrame` 还不是完整 Universe / Renderer 输入状态。 |
| Model 完全锁死 | 未达到 | 后续仍需要整理源码依赖和输出协议。 |

## 4. 关键代码事实

### 4.1 `celengine/model` 仍含 View 可视概念

`BodyFeaturesManager` 管理 `ReferenceMark`：

```text
src/celengine/model/body.h
  class ReferenceMark;
  addReferenceMark(...)
  findReferenceMark(...)
  std::unordered_multimap<const Body*, std::unique_ptr<ReferenceMark>> referenceMarks;

src/celengine/model/body.cpp
  #include <celengine/view3d/referencemark.h>
  Body::recomputeCullingRadius() 调用 ReferenceMark::boundingSphereRadius()
```

判断：

```text
ReferenceMark 当前不是纯 Model 概念。
它既参与 Body culling radius，又包含 View3D render 入口。
这是 Model 与 View3D 混合最明显的一处。
```

后续治理方向：

```text
短期不得迁移到 view3d_legacy 前假装 Model 已干净。
应先拆分“模型侧参考标记状态”和“View3D 渲染表现”。
Body 只应保留可参与物理/选择/边界计算的稳定状态，渲染实现应归 View。
```

### 4.2 `Universe` 仍直接持有可视 Marker 表现

证据：

```text
src/celengine/model/universe.h
  #include <celengine/legacy/marker.h>
  markObject(const Selection&, const celestia::MarkerRepresentation& ...)
  const celestia::MarkerList& getMarkers() const;
  celestia::MarkerList markers;

src/celengine/model/universe.cpp
  Universe::markObject(...) 创建 Marker 并写入 MarkerRepresentation
```

判断：

```text
“对象被标记”可以是 Model/Controller 状态。
但 MarkerRepresentation 是 View 表现参数，当前直接进入 Universe。
```

后续治理方向：

```text
拆分为选择/标记语义状态与 View 表现样式。
Model 可保留 mark/unmark 的语义事实，View 表现应通过 View 状态或渲染配置适配。
```

### 4.3 `OrbitSampler` 在 Model 目录中依赖 View3D 曲线对象

证据：

```text
src/celengine/model/orbitsampler.h
  #include <celengine/view3d/curveplot.h>
  std::vector<CurvePlotSample> samples;
  insertForward(CurvePlot* plot)
  insertBackward(CurvePlot* plot)
```

判断：

```text
轨道采样本身是 Model/数学能力。
CurvePlot / CurvePlotSample 是 View3D 曲线绘制数据结构。
当前文件把两者放在同一头文件里，导致 Model 目录依赖 View3D。
```

后续治理方向：

```text
将采样数据结构拆为纯模型采样点。
把写入 CurvePlot 的适配逻辑放到 View3D 或 View Adapter。
```

### 4.4 `Simulation` 存在 View3D 头文件引用

证据：

```text
src/celengine/controller/simulation.h
  #include <celengine/view3d/texture.h>
```

同时扫描 `simulation.h` 和 `simulation.cpp`，当前只发现该 include，没有发现 `Texture`、`TextureHandle` 或 `TextureResolution` 的实际使用。

判断：

```text
这可能是可直接删除的历史残留，也可能是过去拆分后遗留的头文件污染。
不能仅凭扫描直接删除，必须通过编译验证。
```

后续治理方向：

```text
作为低风险边界清理候选。
删除前先补依赖扫描，删除后必须编译 `celestia_controller`、`celestia-sdl` 和相关测试。
```

### 4.5 `celengine/model` 反向依赖 `celengine/adapter` 生命周期事件

证据：

```text
src/celengine/model/body.cpp
  #include <celengine/adapter/bodylifecycle.h>
  BodyLifecycleEvents::notifyDestroyed(...)
  BodyLifecycleEvents::notifyDefaultPropertiesReset(...)
  BodyLifecycleEvents::hasShapeOverride(...)

src/celengine/model/star.cpp
  #include <celengine/adapter/stardetailslifecycle.h>
  StarDetailsLifecycleEvents::notify...

src/celengine/model/nebula.cpp
  #include <celengine/adapter/nebulalifecycle.h>
  NebulaLifecycleEvents::notifyDestroyed(...)
```

判断：

```text
这些事件本身可以是合理的模型生命周期钩子。
问题是它们目前放在 `adapter` 目录，且主要被 RenderAssets 注册消费。
这形成了“Model 调 Adapter，Adapter 再维护 View/渲染资产”的倒置依赖。
```

后续治理方向：

```text
生命周期事件应迁入 Model/Core 侧的中立位置，或变成明确的底层事件机制。
RenderAssets 可以订阅事件，但 Model 不应 include `celengine/adapter/...`。
```

### 4.6 `celengine/adapter` 是混合层，不是单一 View Adapter

当前 `adapter` 至少包含以下不同职责：

| 模块 | 当前职责 | 审计判断 |
| --- | --- | --- |
| `bodyrenderassets.*` | Body 到 geometry/surface/ring texture 的渲染资产映射 | View/渲染资产适配 |
| `starrenderassets.*` | StarDetails 到 texture/geometry 的渲染资产映射 | View/渲染资产适配 |
| `nebularenderassets.*` | Nebula 到 geometry 的渲染资产映射 | View/渲染资产适配 |
| `solarsys.*` | 解析 Solar System 数据并设置 Body/Surface/RenderAssets | 数据加载 + 渲染资产写入混合 |
| `stardbbuilder.*` | 解析星表并设置 StarRenderAssets | 数据加载 + 渲染资产写入混合 |
| `dsodbbuilder.*` | 解析 DSO 并加载 Nebula render asset | 数据加载 + 渲染资产写入混合 |
| `selectionpicker.*` | 从输入射线选择对象，受 RenderFlags 影响 | Controller/View 交界 |
| `deepskyobjectrenderpolicy.*` | DSO 类型到 RenderFlags/RenderLabels 映射 | View 渲染策略 |
| `sceneviewmodel.*` | Simulation 到 runtime ViewFrame 的投影 | Runtime 输出投影 |

判断：

```text
`adapter` 不是一个稳定边界。
它现在把加载、View 资产、选择拾取、渲染策略、runtime 投影混在一起。
```

后续治理方向：

```text
不要继续把不清楚的代码塞进 adapter。
需要将 adapter 拆成更明确的几个方向：
1. model loading / catalog loading
2. render asset binding
3. picking / controller interaction
4. runtime scene projection
5. legacy View3D compatibility adapter
```

### 4.7 `celruntime/model` 不是纯 Model 层

证据：

```text
src/celruntime/model/modelsnapshot.h
  SimulationBackend::snapshot() 返回 ViewFrame

src/celruntime/model/modelservice.cpp
  ModelService 同时处理 lifecycle、paused、timeScale、cameraFov、cameraPosition、cameraOrbit、selection override、view input label

src/celruntime/model/sceneextractor.cpp
  ViewFrame -> SceneFrame，并带有 fallback body、placeholder mesh/texture、默认 renderSettings

src/celruntime/model/realmodelbackend.cpp
  include <celengine/view3d/meshmanager.h>
  include <celengine/view3d/texmanager.h>
  include <celestia/configfile.h>
  include <celestia/loaddso.h>
  include <celestia/loadsso.h>
  include <celestia/loadstars.h>
```

判断：

```text
`celruntime/model` 当前更准确的名称是 Model host service + runtime projection。
其中 `RealModelBackend` 能加载真实 Celestia 数据，这是有价值成果。
但它通过 View3D 资源路径类和应用层加载函数完成加载，不是干净的纯 Model 后端。
`SceneExtractor` 输出的是面向 View 的渲染状态，不是 Model 自身完整状态。
```

后续治理方向：

```text
保留真实加载成果。
但要把 RealModelBackend 的应用层加载依赖、View3D 路径类依赖和 SceneFrame 投影依赖分层隔离。
Runtime Model 输出应区分：
- ModelSnapshot：模型事实状态
- SceneProjection：供 View 消费的投影状态
- SceneFrame：跨进程协议消息
```

## 5. 当前扫描机制缺口

当前 `tools/mvc/scan_mvc_dependencies.ps1` 可以通过：

```text
MVC dependency scan passed
```

但它主要检查：

```text
src/celruntime/protocol 不 include SDL / OpenGL / celrender / celengine/view3d
部分 runtime / SDL 源码中不保留旧 Step6 fallback
根转发头残留
```

它没有覆盖：

```text
src/celengine/model -> src/celengine/view3d
src/celengine/model -> src/celengine/adapter
src/celengine/controller -> src/celengine/view3d
src/celengine/adapter -> src/celruntime
src/celruntime/model -> src/celengine/view3d / src/celestia
```

因此，不能用现有扫描通过来证明 Model 层已经解耦干净。

后续必须新增更强的边界扫描，建议先以报告模式运行，再逐步转为失败门槛。

## 6. Model 锁死状态重新定义

从现在起，Model 锁死不能再用一个笼统说法。必须分级：

| 级别 | 名称 | 当前状态 | 判定 |
| --- | --- | --- | --- |
| L1 | 原核心能力未重写 | 已达到 | 仍使用原 Celestia 核心对象。 |
| L2 | 可运行真实 Model 后端 | 基本达到 | `RealModelBackend` 能加载真实数据并输出早期 `ViewFrame`。 |
| L3 | CMake 初步分层 | 部分达到 | 对象库已拆分，但最终链接和源码依赖仍混杂。 |
| L4 | Model 源码不反向依赖 View/Adapter | 未达到 | 存在 `ReferenceMark`、`CurvePlot`、`MarkerRepresentation`、生命周期 adapter 等反向依赖。 |
| L5 | Model 输出协议覆盖完整核心状态 | 未达到 | 当前输出偏 selection / simplified scene projection。 |
| L6 | Model 层完全不动 | 未达到 | 后续仍要清理依赖和输出边界。 |

可接受说法：

```text
Step18 是真实核心能力可运行的中间态。
Step18 不等于 Model 完全锁死。
后续 Model 侧只能做边界清理、输出投影整理和依赖治理，不应重写核心天体计算能力。
```

不可接受说法：

```text
Model 层已经完全切干净。
Model 层已经完全不需要再动。
View3D 迁移只需要处理 View 文件夹。
现有 `ViewFrame` / `SceneFrame` 已经完整表达原 Celestia 渲染所需全部状态。
```

## 7. 后续治理顺序

### Step19.0A 边界扫描增强

目标：

```text
新增报告模式扫描，列出 Model / Controller / Adapter / Runtime Model 的反向依赖。
先不作为失败门槛，避免当前基线立即无法验证。
```

当前实现：

```text
tools/mvc/scan_mvc_boundary_debt.ps1
test/scripts/test_mvc_boundary_debt_scan.ps1
```

使用方式：

```powershell
# 报告模式，发现问题也返回 0
powershell -NoProfile -ExecutionPolicy Bypass -File tools\mvc\scan_mvc_boundary_debt.ps1

# 门槛模式，发现问题返回非 0，供未来清理后纳入强制验证
powershell -NoProfile -ExecutionPolicy Bypass -File tools\mvc\scan_mvc_boundary_debt.ps1 -FailOnFindings
```

建议覆盖：

```text
model -> view3d / celrender
model -> adapter
controller -> view3d / celrender
adapter -> runtime
runtime/model -> view3d / celestia application loaders
```

当前报告模式已覆盖：

```text
model->view
model->adapter
model-view-symbol
controller->view
adapter->runtime
adapter->view
runtime-model->view
runtime-model->app
runtime-model-projection
```

当前真实仓库报告结果：

```text
MVC boundary debt scan report: 88 finding(s)
adapter->runtime: 1
adapter->view: 12
controller->view: 1
model->adapter: 4
model->view: 2
model-view-symbol: 18
runtime-model->app: 4
runtime-model->view: 2
runtime-model-projection: 44
```

解释：

```text
这 88 项不是新增退化，而是把 Step19.0 审计中已经发现的边界债稳定机器化。
当前默认报告模式不阻断现有构建和回归。
只有完成对应清理后，才能考虑把 -FailOnFindings 纳入强制门槛。
```

### Step19.0B 低风险源码边界清理候选

候选：

```text
删除 simulation.h 中疑似未使用的 view3d/texture.h include。
将 OrbitSampler 的纯采样数据与 CurvePlot 写入逻辑拆开。
将生命周期事件从 adapter 迁到更中立的 model/core lifecycle 位置。
```

这些候选必须逐项编译验证，不允许批量修改。

### Step19.0C 中高风险边界拆分候选

候选：

```text
ReferenceMark 拆分为模型侧参考标记状态与 View3D 渲染表现。
Universe MarkerRepresentation 拆分为标记语义与 View 表现。
solarsys/stardbbuilder/dsodbbuilder 拆分数据加载与渲染资产绑定。
RealModelBackend 拆分真实数据加载、ModelSnapshot 生成和 SceneProjection 输出。
```

这些候选影响面大，必须在 Step19.0A 扫描和 Step19.0B 小清理完成后再执行。

### Step19.1 原 View3D 源码归属矩阵

只有 Step19.0 至少完成审计并确认治理顺序后，才能进入原 View3D 源码归属矩阵。

Step19.1 的对象不只是：

```text
src/celengine/view3d/
src/celrender/view3d/
src/celestia/
```

还必须包含本审计发现的交界对象：

```text
ReferenceMark
MarkerRepresentation / MarkerList
CurvePlot / OrbitSampler
BodyRenderAssets / StarRenderAssets / NebulaRenderAssets
SelectionPicker
SceneViewModel / SceneExtractor / ViewFrame
RealModelBackend 的加载依赖
```

## 8. 对 View3D 迁移的影响

本审计改变 Step19 的执行顺序：

```text
错误顺序:
  直接建立 view3d_legacy -> 迁移 View3D Renderer -> 再回头处理 Model 污染

正确顺序:
  Step19.0 边界复审
  -> Step19.0A 扫描增强
  -> Step19.0B 低风险边界清理
  -> Step19.1 原 View3D 源码归属矩阵
  -> Step19.2 模板 View 最小骨架
  -> Step19.3 第一个低风险白盒迁移
```

原因：

```text
如果 Model/Controller 边界不先确认，View3D 迁移会把历史混合依赖一起带进新目录。
那样得到的不是平权 View，而是换了目录名的特殊 View3D。
```

## 9. 当前阶段验收口径

本审计完成后，只能声明：

```text
已识别 Step18 Model/Controller/View 边界的主要污染点。
已确认 Step18 不是 Model 完全锁死点。
已确定 View3D 模板迁移前必须补 Step19.0 边界治理。
```

不能声明：

```text
污染点已经修复。
Model 层已经清理完成。
View3D 模板迁移已经具备直接执行条件。
```
