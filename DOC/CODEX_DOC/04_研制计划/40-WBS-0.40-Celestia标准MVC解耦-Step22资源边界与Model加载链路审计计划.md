# Celestia 标准 MVC 解耦 Step22 资源边界与 Model 加载链路审计计划

## 1. 背景

Step21 已经把 `SolarSystem` / `SolarSystemCatalog` 从 `adapter` 迁回 `model`，并通过边界扫描确认 `src/celengine/model` 目录内不再直接依赖 `adapter`。这个结果只说明“Model 目录内直接 Adapter 依赖”被清除，并不等价于 Model 层整体完成解耦。

当前继续暴露出的关键问题不是单一类移动，而是三类边界混在一起：

1. 数据对象构建链路仍然同时处理模型数据、资源路径、纹理/几何句柄和 View3D 相关资源。
2. `RealModelBackend` 为了加载真实 Celestia 数据，直接依赖应用层加载器和 View3D 资源管理类型。
3. 运行时输出仍然以历史性的 `ViewFrame` 为主，尚未形成明确的 `ModelSnapshot -> SceneProjection -> SceneFrame` 分层。

因此 Step22 不直接改源码，先做专项源码审计，目标是把后续 Model 层继续解耦所需的“事实边界”和“拆分候选点”分析清楚。

## 2. Step22 目标

Step22 的目标是产出一份可供后续编码阶段使用的源码审计分析，而不是直接完成重构。

具体目标：

1. 明确 Adapter、资源路径索引、渲染资源外挂、View3D 私有资源、运行时输出之间的真实关系。
2. 对 `SolarSystemsBuilder`、`StarDatabaseBuilder`、`DSODatabaseBuilder` 三条加载/构建链路进行横向对比。
3. 对 `Surface`、`Atmosphere`、`BodyRenderAssets`、`StarRenderAssets`、`NebulaRenderAssets` 进行分层归类。
4. 解释 `RealModelBackend` 的来源、职责、依赖和目前不干净的位置。
5. 形成 Step23 及后续代码拆分的候选路线，但不把未验证的路线包装成已完成结论。

## 3. 非目标

Step22 明确不做以下事情：

1. 不修改 C++ 源码。
2. 不移动 View3D 目录或重命名旧 View。
3. 不宣称 Model 层已经完成整体解耦。
4. 不直接设计新 View3D，也不继续仿照效果实现 View。
5. 不把资源句柄替换为新类型，除非进入后续明确编码步骤。

## 5. 分析口径

为避免再用过粗的“渲染相关就移走”判断，Step22 按以下口径审计。

| 口径 | 定义 | 初步处理方向 |
|---|---|---|
| 纯 Model 状态 | 天体、轨道、时间、目录、索引、物理参数、层级关系 | 应保留在 Model |
| Model 视觉属性 | 反照率、颜色、云层高度、散射参数、材质数值等影响可视化但不绑定具体渲染后端的属性 | 可能保留在 Model，但要和具体资源句柄分离 |
| 资源引用 | 纹理名、网格名、资源逻辑 ID、资源路径候选 | 可作为跨 View 的资源描述或资源索引输入 |
| 资源路径索引 | 把逻辑资源名解析到实际文件路径的能力 | 可作为多 View 共用基础能力，但不能直接绑定 View3D 实现 |
| 外挂渲染资源 | 按 Model 对象指针挂接纹理/几何句柄的映射表 | 当前是过渡形态，需要判断能否抽象为跨 View 资源描述 |
| View3D 私有资源 | OpenGL/纹理管理器/几何管理器/渲染对象/渲染缓存 | 应属于 View3D 私有实现 |
| 运行时投影 | 把 Model 状态转换为某个 View 或进程通信可消费的数据结构 | 不应反向污染 Model |
| 应用加载器 | 配置文件、数据目录、星表/深空/太阳系文件加载入口 | 当前可被后端复用，但层级需要明确 |

## 6. 执行步骤

### Step22-A：冻结事实基线

1. 记录当前分支、提交和工作区状态。
2. 执行 MVC 边界扫描，记录发现数量和类型。
3. 确认 Step22 只产生文档变更。

验收方式：

1. 文档中包含扫描结果摘要。
2. `git status` 能清楚显示 Step22 只新增或修改文档。

### Step22-B：Builder 横向审计

分析三条构建链路：

1. `SolarSystemsBuilder`
2. `StarDatabaseBuilder`
3. `DSODatabaseBuilder`

每条链路都按同一张表审计：

1. 输入来源。
2. 创建的 Model 对象。
3. 写入的 Model 数据。
4. 写入的资源引用或资源句柄。
5. 使用的 Adapter / View3D / App 层依赖。
6. 可拆分的最小候选单元。

验收方式：

1. 分析文档中三条链路具备同口径对比。
2. 能回答为什么 Step21 单独处理了 `SolarSystem`，以及为什么 Builder 仍需后续处理。

### Step22-C：资源外挂与资源路径审计

分析以下对象：

1. `TexturePaths`
2. `GeometryPaths`
3. `BodyRenderAssets`
4. `StarRenderAssets`
5. `NebulaRenderAssets`
6. `NebulaRenderAssetLoader`

重点回答：

1. 哪些只是资源索引。
2. 哪些已经是 View3D 私有句柄。
3. 哪些看起来像多 View 共用基础能力，但目前仍被 View3D 类型污染。
4. 哪些可以留作连接层基础能力，哪些必须进入具体 View 私有目录。

验收方式：

1. 分析文档中给出资源对象归类表。
2. 明确 Adapter 当前不是一个干净的多 View 资源服务。

### Step22-D：`Surface` / `Atmosphere` 审计

分析 `Surface` 与 `Atmosphere` 字段，区分：

1. 物理/视觉数值属性。
2. 材质和外观参数。
3. 纹理句柄或资源引用。
4. 与具体渲染后端绑定的字段。

验收方式：

1. 文档中给出字段级或字段组级分类。
2. 明确这两个类型不是简单“全部属于 View”或“全部属于 Model”，而是需要拆分资源引用边界。

### Step22-E：`RealModelBackend` 审计

分析 `RealModelBackend` 当前职责：

1. 读取 Celestia 配置。
2. 建立纹理/几何路径。
3. 调用星表、深空、太阳系加载器。
4. 创建 `Universe` 和 `Simulation`。
5. 从 `Simulation` 输出历史性 `ViewFrame`。

重点回答：

1. 它为什么出现。
2. 它是不是原始 Celestia 代码。
3. 它为什么依赖 App 层加载器和 View3D 类型。
4. 它后续应该拆成哪些更小职责。

验收方式：

1. 文档中明确 `RealModelBackend` 的过渡性质。
2. 文档中列出后续拆分候选，而不是直接宣称它已经合理。

### Step22-F：运行时输出链路审计

审计以下链路：

`Simulation -> SceneViewModel -> ViewFrame -> SceneExtractor -> SceneFrame`

重点回答：

1. `ModelSnapshot` 为什么现在名义上存在但实际仍返回 `ViewFrame`。
2. `SceneViewModel` 为什么形成 `adapter -> runtime` 依赖。
3. `SceneExtractor` 为什么在 runtime/model 内接触 View 投影状态。
4. 后续要形成什么样的输出分层。

验收方式：

1. 文档中区分历史过渡结构和目标结构。
2. 不把 `ViewFrame` 当成最终 Model 输出规范。

### Step22-G：形成后续工作建议

输出 Step23 及后续候选路线：

1. 先抽象资源引用与资源注册表。
2. 再拆 Builder 的数据构建与资源绑定。
3. 再处理 `RealModelBackend` 的加载职责。
4. 再替换运行时输出链路中的 `ViewFrame`。
5. 最后再谈 View 模板平权迁移。

验收方式：

1. 文档中给出优先级和风险说明。
2. 结论明确哪些是“已经完成”、哪些只是“下一步候选”。

## 9. 风险

| 风险 | 说明 | Step22 处理方式 |
|---|---|---|
| 把资源路径误判为 View 私有实现 | 纹理/网格路径可能是多 View 共用能力，不应粗暴删除 | 先分类，再决定是否抽象 |
| 把 `Surface` / `Atmosphere` 整体移走 | 二者包含物理/视觉属性，也包含资源句柄 | 做字段组分类 |
| 把 `RealModelBackend` 当成最终架构 | 它是为了真实数据后端引入的过渡加载入口 | 只审计，不固化为终局 |
| 把扫描台账当成充分验收 | 扫描只能证明某类依赖是否存在，不能证明业务层解耦完成 | 扫描结果只作为证据之一 |
| 继续做效果导向 View 实现 | 会偏离“基于现有业务代码切分”的主线 | Step22 不做新 View 效果实现 |

## 10. 完成判定

Step22 完成的判定是：

1. 上述两份文档存在且内容完整。
2. 分析文档能回答 Adapter、RealModelBackend、Surface、Atmosphere 的定位问题。
3. 分析文档能说明 Builder 家族后续拆分原因。
4. 文档验证命令通过或明确记录异常原因。
5. 没有修改 C++ 源码。

Step22 完成后，项目仍不应被描述为“Model 层完全解耦”。更准确的描述应是：已完成 Model 目录直接 Adapter 依赖清理，并形成下一轮资源边界与加载链路拆分的源码审计依据。
