# Celestia 标准 MVC 解耦 Step20 Model 层进一步解耦计划

> 本文是审阅版计划，用于在原 View3D 模板 View 迁移前，先把 Model 层进一步解耦的工作对象、执行顺序、验证口径和暂停条件讲清楚。本文不改源码，不代表阶段已经通过验收。

## 1. 目标

Step20 的目标不是重写 Celestia 的天体计算核心，而是在保留原始核心能力的前提下，把当前仍混在 Model、Controller、Adapter、Runtime Projection、View3D 之间的依赖和职责逐步理顺。

本阶段完成后，应达到以下状态:

1. Model 相关源码实体有清晰归属矩阵，能说明每个类/文件属于纯 Model、Model 计算、Controller 状态、加载构建、渲染资源绑定、View3D 私有实现、Runtime 投影中的哪一类。
2. Model 层反向依赖 View3D、celrender、UI、Adapter 混合职责的债务被逐项识别、分级、治理或明确暂缓。
3. `Simulation`、`Observer`、`ObserverFrame`、`Selection` 的职责边界被重新确认，避免把运行会话状态误认为纯 Model 对象图。
4. `BodyFeaturesManager`、`BodyRenderAssets`、`ReferenceMark`、`MarkerRepresentation`、`OrbitSampler` 等交界对象被拆成可执行治理任务。
5. Runtime Model 输出被区分为 Model 事实状态、Scene 投影状态、跨进程消息三层，避免把当前 `SceneFrame` 当作完整 Model 状态。
6. 单 exe 原能力、真实 Model 后端、多进程 runtime 的验证路径保持连续，不能为了边界清理破坏已有能力。

## 2. 当前事实依据

本计划基于以下已经确认的当前事实:

| 事实 | 说明 |
| --- | --- |
| Step18 是可运行中间态 | 它证明统一 exe 回归、真实 Model 后端、runtime smoke 和截图矩阵可以工作，但不是 Model 完全锁死点 |
| 真实 Model 后端已存在 | `RealModelBackend` 能复用真实加载链创建 `Universe` 和 `Simulation`，但它仍带有应用层加载和 View3D 资源路径依赖 |
| Model 源码边界仍不干净 | 已发现 `ReferenceMark`、`MarkerRepresentation`、`OrbitSampler`、生命周期事件、Adapter 混合职责等问题 |
| View3D 迁移不能先行 | 如果 Model/Controller/Adapter 边界不先治理，`view3d_legacy` 会把历史混合依赖一起带入新目录 |
| 现有扫描不足以验收 | `scan_mvc_dependencies.ps1` 通过不等于 Model 干净；`scan_mvc_boundary_debt.ps1` 已补充报告模式，但当前债务清单不能直接等同最终验收 |

当前边界债务的代表性证据:

| 编号 | 问题 | 当前证据 | 风险 |
| --- | --- | --- | --- |
| M1 | Model 依赖 View3D 概念 | `BodyFeaturesManager` 管理 `ReferenceMark`，`body.cpp` 读取 View3D 参考标记能力 | 把显示标注误留在 Model 内 |
| M2 | Universe 持有可视化标记表现 | `Universe` 管理 `MarkerRepresentation` / `MarkerList` | 对象标记语义和 View 表现参数混在一起 |
| M3 | 轨道采样依赖 View 曲线对象 | `OrbitSampler` 使用 `CurvePlot` / `CurvePlotSample` | Model 数学采样和 View 绘制结构耦合 |
| M4 | Controller 存在 View3D 头文件残留 | `simulation.h` include `view3d/texture.h` | Controller 独立性不足，可能是低风险残留 |
| M5 | Model 反向依赖 Adapter 生命周期事件 | `Body` / `Star` / `Nebula` 调用 adapter lifecycle | Model 事件机制和渲染资产刷新机制倒置 |
| M6 | Adapter 混合过多职责 | builder、render assets、picker、projector、render policy、scene projection 混在 `adapter` | 目录名不能代表真实层次 |
| M7 | Runtime Model 输出层次不清 | `ViewFrame`、`SceneExtractor`、`SceneFrame` 混合真实状态和 View 投影 | 后续协议可能覆盖不足或语义不稳定 |

## 3. 非目标

本阶段不做以下事情:

1. 不重写 `Universe`、`Body`、`Star`、`DeepSkyObject`、`Timeline`、`ReferenceFrame` 的核心天体计算能力。
2. 不开始原 View3D renderer 大规模迁移。
3. 不把 `SceneFrame` 扩展成一个号称完整表达全部 Celestia 状态的万能格式。
4. 不因为扫描清单减少就宣布 Model 完全解耦。
5. 不用弱化 visual runtime 效果替代统一 exe 原能力回归。
6. 不机械移动文件；只有职责单一且验证通过的文件才允许整体迁移，其余必须拆分、适配或暂缓。

## 4. Model 锁定分级

为避免“Model 锁死”概念再次混淆，后续统一采用分级判断。

| 级别 | 名称 | 当前判断 | 进入条件 |
| --- | --- | --- | --- |
| L1 | 原核心能力未重写 | 已达到 | 仍使用原 Celestia 核心对象和加载链 |
| L2 | 真实 Model 后端可运行 | 基本达到 | `RealModelBackend` 能加载真实数据并输出可消费状态 |
| L3 | 构建目标初步分层 | 部分达到 | `celestia_model`、`celestia_controller`、`celestia_view_adapter` 等目标存在且可构建 |
| L4 | Model 源码不反向依赖 View/Adapter 混合职责 | 未达到 | Model 不再 include View3D/celrender/UI，不再直接依赖 Adapter 中的渲染资产机制 |
| L5 | Model 输出覆盖后续 View 所需核心状态 | 未达到 | 原 View3D 读取链已反查，ModelSnapshot / SceneProjection / SceneFrame 分层明确 |
| L6 | Model 层完全不动 | 未达到 | L4/L5 达到，且后续 View 迁移只修改输出适配或 View 私有实现 |

本计划的直接目标是推进 L4 和 L5，不承诺本轮直接达到 L6。

## 5. 总体执行策略

执行顺序必须是:

```text
源码事实归属矩阵
-> 边界债务扫描和分级
-> 低风险依赖清理
-> 中高风险交界对象拆分
-> Runtime Model 输出分层
-> 回归验证和阶段判断
-> 再进入 View3D 模板 View 迁移
```

不能采用以下顺序:

```text
先建 view3d_legacy
-> 搬 renderer
-> 遇到编译错误再临时修 Model
-> 最后补解释
```

原因是后一种顺序会把历史混合依赖带入新的 View 目录，形成“换了位置的特殊 View3D”，不满足后续多种 View 平权替换的目标。

### WP1. Model 源码实体归属矩阵

目标:

建立一份可审阅的源码实体归属矩阵，覆盖 Model、Controller、Adapter、Runtime Model、原 View3D 的交界对象。

覆盖范围:

```text

src/celengine/adapter/
src/celruntime/model/
src/celruntime/viewframe.h
src/celruntime/protocol/sceneprotocol.h
```

| 字段 | 要求 |

| 源码身份 | class、struct、free function、全局 manager、CMake target |

| 当前消费者 | 谁 include、谁调用、谁持有、谁读取 |
| 初步归属 | 纯 Model、Model 计算、Controller 状态、加载构建、渲染资产绑定、View3D 私有、Runtime 投影、暂缓判断 |
| 治理方式 | 保留、移动、拆分、抽接口、转到 shared、转到 View、暂缓 |
| 验证方式 | 对应编译目标、CTest、扫描项、回归脚本 |

```text

```

完成标准:

1. 不能只按目录归类，必须按源码实体归类。
2. `Selection`、`Observer`、`ReferenceFrame`、`Timeline`、`BodyFeaturesManager` 等已被反复讨论的对象必须单独列出。
3. 每个“暂缓判断”都必须写明暂缓原因和重新判断入口。

### WP2. 边界债务扫描强化

目标:

把当前人工发现的边界债务转成稳定扫描机制，但扫描机制只作为证据入口，不作为唯一验收结论。

当前已有:

```text
tools/mvc/scan_mvc_boundary_debt.ps1
test/scripts/test_mvc_boundary_debt_scan.ps1
```

需要强化:

| 类别 | 扫描方向 |
| --- | --- |
| model->view | `src/celengine/model` include 或符号引用 `view3d` / `celrender` |
| model->adapter | `src/celengine/model` include `celengine/adapter` |
| controller->view | `src/celengine/controller` include 或符号引用 `view3d` / `celrender` |
| adapter->runtime | `src/celengine/adapter` include `celruntime` |
| runtime-model->view | `src/celruntime/model` include `view3d` / `celrender` |
| runtime-model->app | `src/celruntime/model` include `src/celestia` 应用层加载入口 |
| runtime-model-projection | `ViewFrame` / `SceneFrame` 中明显属于 View 投影而非 Model 事实的字段 |

执行策略:

1. 报告模式保持可运行，不阻塞当前基线。
2. 每治理一类债务，就把该类转换为更严格的断言。
3. 不允许为了扫描通过而隐藏 include 或改名规避。

完成标准:

1. 扫描报告能稳定复现当前债务数量和分类。
2. 每个分类都有对应的解释和治理计划。
3. `-FailOnFindings` 只在对应分类治理完成后分批启用。

### WP4. Model 生命周期事件中立化

目标:

治理 `Body`、`Star`、`Nebula` 等 Model 对象反向 include `adapter` 生命周期事件的问题。

这个问题不能简单定性为“原始设计不合理”。更客观的判断是:

1. 在原始单体式 Celestia 中，Model 对象生命周期和渲染资源缓存处在同一个进程、同一个应用组织里，生命周期通知直接服务渲染资产刷新是可以工作的工程实现。
2. 早期系统目标不是标准 MVC 平权 View，因此“Model 对象变化后通知渲染资产缓存失效”没有被严格要求成单向依赖。
3. 后续我们把源码按 MVC 目标拆分后，这种原本可运行的进程内协作关系暴露为边界债务: Model 侧 include 了位于 `adapter` 的生命周期事件，而这些事件主要被 RenderAssets 消费。
4. 因此本阶段要治理的不是“否定原始实现”，而是把可运行的历史协作方式改造成标准 MVC 下更稳定的依赖方向: Model 只发布生命周期事实，渲染资产或 View Adapter 订阅并处理缓存更新。

当前问题:

```text
src/celengine/model/body.cpp   -> celengine/adapter/bodylifecycle.h
src/celengine/model/star.cpp   -> celengine/adapter/stardetailslifecycle.h
src/celengine/model/nebula.cpp -> celengine/adapter/nebulalifecycle.h
```

建议方向:

1. 把生命周期事件机制移动到 Model/Core 中立位置，例如 `src/celengine/model/lifecycle/` 或同级更合适位置。
2. Model 只发布对象生命周期事件。
3. RenderAssets 或 View Adapter 订阅事件并维护渲染资产缓存。
4. Model 不 include `celengine/adapter/...`。

风险:

这类事件可能直接影响资源缓存清理和默认属性重置，不能只靠编译判断通过。

完成标准:

1. Model 到 Adapter 的对应 include 消失。
2. RenderAssets 仍能收到销毁和属性重置事件。
3. 单 exe Quick 回归通过。
4. 资源缺失、fallback、选择、地表对象场景不退化。

### WP5. OrbitSampler 与 View 曲线绘制拆分

目标:

把轨道采样的数学/Model 能力和 View 曲线绘制对象分开。

当前问题:

```text
src/celengine/model/orbitsampler.h
  include <celengine/view3d/curveplot.h>
  使用 CurvePlot / CurvePlotSample
```

建议方向:

1. 定义纯 Model 采样点结构，例如 `OrbitSamplePoint`，只表达时间、位置、有效性、分段语义。
2. `OrbitSampler` 只产生纯采样点序列。
3. View3D 或 Adapter 提供 `OrbitSamplePoint -> CurvePlot` 的转换。
4. Runtime SceneProjection 使用纯采样点生成跨进程输出。

验证重点:

1. 原 View3D 轨道显示不退化。
2. Runtime orbit sample 字段继续稳定。
3. Model 不再 include `curveplot.h`。

### WP6. ReferenceMark / Marker 表现拆分

目标:

拆分对象标记的语义状态和 View3D 表现。

当前问题:

| 对象 | 当前混合点 |
| --- | --- |
| `ReferenceMark` | Model 通过 `BodyFeaturesManager` 管理，但它包含 View3D 渲染入口或表现能力 |
| `MarkerRepresentation` | `Universe` 持有标记列表时携带 View 表现参数 |
| `Body::recomputeCullingRadius` | 可能读取参考标记边界半径，说明部分标记信息又参与可见性/边界计算 |

建议方向:

1. 区分 Model 侧标记语义，例如“某对象被标记”“标记类型”“标记参与边界计算的数据”。
2. 区分 View 侧表现，例如图标、颜色、线宽、渲染样式、OpenGL 绘制。
3. `Universe` 或 Controller 可以保留标记语义，但不直接持有 View 表现结构。
4. View3D 通过 Adapter 或 View 状态把语义标记转换成可渲染表现。

风险:

这部分可能影响 UI 标记、脚本标记、对象选择、边界半径、可见性裁剪，属于中高风险。

完成标准:

1. `Universe` 不直接依赖 View 表现类型。
2. `BodyFeaturesManager` 中与显示强相关的数据有明确归属。
3. 标记相关脚本和原 UI 行为通过回归或人工场景验证。

### WP7. Adapter 分层治理

目标:

把 `src/celengine/adapter` 从混合目录拆成更明确的职责组，不再让“adapter”成为所有边界不清代码的收纳处。

当前至少存在五类职责:

| 职责 | 代表对象 |
| --- | --- |
| 数据加载/对象构建 | `stardbbuilder.*`、`dsodbbuilder.*`、`solarsys.*` |
| 渲染资产绑定 | `bodyrenderassets.*`、`starrenderassets.*`、`nebularenderassets.*` |
| 拾取和交互 | `selectionpicker.*`、`deepskyobjectpicker.*` |
| 几何/场景投影 | `bodylocationgeometryprojector.*`、`sceneviewmodel.*` |
| 渲染策略 | `deepskyobjectrenderpolicy.*` |

建议方向:

1. 加载构建能力向 model loading / catalog loading 方向命名和归属。
2. 渲染资产绑定保持为 View/Render Asset Binding，不再被 Model 直接依赖。
3. 拾取逻辑归入 Controller/View 交界，不进入纯 Model。
4. Runtime 投影独立为 Runtime Projection，不和 Model 本体混用。

完成标准:

1. Adapter 内部每类职责有明确目标归属。
2. 新增或移动文件前先更新实体归属矩阵。
3. 不能出现“移动到 adapter 就算解决”的结论。

### WP8. Simulation / Observer / Selection 职责边界重审

目标:

把运行会话、观察者、当前选择、对象引用和 Model 对象图之间的关系讲清楚，并据此治理源码依赖。

当前判断:

| 对象 | 当前定位 |
| --- | --- |
| `Universe` | Model 对象目录和对象图入口 |
| `Simulation` | 运行会话根对象，持有 `Universe`，管理时间、观察者、选择、运行控制 |
| `Observer` | 观察者状态，包含位置、姿态、速度、旅行动作 |
| `ObserverFrame` | Controller 侧对 `ReferenceFrame` 的受限包装 |
| `Selection` | typed handle，不是数据管理器，不是对象索引 |

治理重点:

1. 不把 `Selection` 提高成 Model 管理中心。
2. 不把 `Universe` 扩展成观察者视角或当前运行状态容器。
3. 判断 `Simulation` 是否需要拆分出更清晰的 ModelSession / ControllerSession / RuntimeSession 边界。
4. `ObserverFrame` 继续使用 `ReferenceFrame` 时，要明确它是 Controller 包装，不改变 `ReferenceFrame` 的 Model 计算属性。

完成标准:

1. `Simulation` 的职责边界有清晰文档和代码证据。
2. 任何实际代码调整都有回归覆盖时间推进、选择、跟随、goto、center、pause、time scale。
3. 单 exe 和 multi-process 的交互语义保持一致。

### WP9. Runtime Model 输出分层

目标:

把 runtime 的 Model 输出拆成三层，避免后续 View 迁移时误以为当前 `SceneFrame` 已经覆盖完整 Model 能力。

目标分层:

| 层 | 含义 | 代表产物 |
| --- | --- | --- |
| ModelSnapshot | Model 事实状态，尽量不携带 View 表现 | 时间、对象引用、catalog 摘要、observer 事实状态、选择语义、轨道采样事实 |
| SceneProjection | 面向 View 的投影结果 | 可见对象、几何、资源引用、标签候选、渲染参数候选 |
| SceneFrame | 跨进程消息格式 | runtime protocol payload，稳定传输 SceneProjection |

治理重点:

1. `RealModelBackend` 不应长期直接输出 View 投影对象。
2. `SceneExtractor` 的职责应明确为投影，不是 Model 本体。
3. `ViewFrame` 命名和职责需要复审，避免它同时表示 Model 后端快照和 View 输入。
4. 原 View3D 读取链完成前，不冻结最终输出规范。

完成标准:

1. 三层输出职责写入规范或设计说明。
2. Step12-17 相关 runtime 测试继续通过。
3. 原 View3D 读取链能映射到 ModelSnapshot / SceneProjection / SceneFrame 的某一层。

## 7. 阶段顺序和建议拆分

建议把 Step20 分成四个小阶段:

| 阶段 | 名称 | 主要产物 | 是否改 C++ |
| --- | --- | --- | --- |
| 20A | 实体归属矩阵和扫描基线 | 02-10 归属矩阵、扫描报告更新 | 否，除非补扫描脚本 |
| 20B | 低风险边界清理 | include 清理、扫描分类收紧、 focused build | 是，低风险 |

## 9. 暂停和回滚条件

出现以下情况必须暂停:

1. Quick 回归截图或 runtime smoke 失败。
2. `celestia-sdl` 或 unit 构建失败，且不是明显测试脚本问题。
3. 一个对象无法判断归属，却已经被计划移动。
4. 为了通过编译引入新的反向依赖。
5. 删除或移动了原 View3D 使用路径，但没有对应的兼容验证。
6. 扫描数量下降，但实际职责只是换名或换目录，没有真正分层。

回滚原则:

1. 小切片失败，优先回滚该切片，不继续叠加修复。
2. 如果失败发生在中高风险拆分，先恢复原行为，再重新拆分计划。
3. 任何影响单 exe 原能力的改动都不能带病进入下一阶段。

## 10. 与 View3D 模板迁移的关系

Step20 是 View3D 模板迁移的前置治理阶段。

只有满足以下条件，才建议进入 `view3d_legacy` 模板 View 的实际源码迁移:

1. Model 实体归属矩阵完成并通过审阅。
2. 低风险边界清理完成。
3. `OrbitSampler`、生命周期事件、`ReferenceMark`、`MarkerRepresentation` 等关键交界对象至少有明确治理结论。
4. Runtime Model 输出分层方向明确。
5. 扫描债务不是简单清零，而是能解释剩余债务为什么暂缓、何时处理。
6. 单 exe Quick 回归和相关 runtime 测试保持通过。

如果这些条件不满足，直接迁移 View3D 会导致新模板 View 继续依赖旧特殊位置，不符合“所有 View 平权”的目标。
